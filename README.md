# Catan Web

Онлайн-гра Catan у 2D для 3–4 гравців із вебінтерфейсом для комп’ютерів і телефонів.

Проєкт перебуває на початковому етапі. Репозиторій організований як npm
workspaces; базові каркаси клієнта, сервера та спільних пакетів уже створені,
а клієнт поки виводить лише «Hello World». Ігрові правила й функціональні
модулі реалізовуватимуться поступово.

## Стек

| Частина | Технології |
| --- | --- |
| Мова клієнта, сервера та правил | TypeScript |
| Клієнт | React, Vite |
| Поле, графіка та анімації | SVG, CSS |
| Сервер | Node.js 24 LTS, Fastify |
| Онлайн-взаємодія | Socket.IO |
| База даних | PostgreSQL |
| Організація репозиторію | npm workspaces, один кореневий lockfile |
| Перевірки | TypeScript, ESLint, Vitest; Playwright для браузерних сценаріїв |
| Розміщення | Debian 12, Nginx, systemd |
| Автоматизація | GitHub Actions |

## Структура

Клієнт і сервер — окремі застосунки в одному репозиторії. Правила гри винесені
в окремий пакет, а формати обміну даними — у спільний пакет.

| Шлях | Призначення |
| --- | --- |
| `apps/client/` | Вебзастосунок і його збірка |
| `apps/client/src/styles/` | Кольори, типографіка, відступи, адаптивні макети та CSS-анімації |
| `apps/client/src/assets/` | Зображення, текстури, іконки та шрифти |
| `apps/client/src/components/` | Візуальні компоненти: кнопки, панелі, карти й SVG-поле |
| `apps/client/src/pages/` | Компонування сторінок входу, лобі та партії |
| `apps/client/src/state/` | Клієнтський стан: отримані дані, вибір користувача, відкриті панелі |
| `apps/client/src/network/` | HTTP-запити, Socket.IO, відправлення команд і перепідключення |
| `apps/server/src/` | Акаунти, кімнати, HTTP API, обробники Socket.IO та доступ до БД |
| `apps/server/migrations/` | Версіоновані зміни схеми PostgreSQL |
| `packages/game/src/` | Правила, перевірка дій, переходи стану та підрахунок результатів |
| `packages/game/tests/` | Тести ігрових правил |
| `packages/shared/src/` | Публічні типи та схеми перевірки команд і відповідей |
| `deploy/` | Конфігурація Nginx, systemd та сценарії розгортання без секретів |
| `.github/workflows/` | Перевірки pull request і деплой |

## Межі між частинами

- **Оформлення:** стилі та графічні ресурси змінюються в `styles/` і `assets/`.
  Компоненти й сторінки відповідають за вигляд, адаптивність і доступність.
  Зміна дизайну не повинна потребувати змін у сервері або правилах гри.
- **Клієнт:** показує отриманий стан і надсилає наміри гравця, наприклад
  побудувати дорогу. Вибір елемента, відкриття панелі й анімація — клієнтська
  логіка; списання ресурсів та визначення переможця — правила гри.
- **Сервер:** визначає користувача, перевіряє його право діяти, застосовує
  правила з `packages/game`, зберігає результат і розсилає оновлення.
  Приховані карти та інші приватні дані не передаються чужим клієнтам.
- **Правила:** `packages/game` не залежить від React, CSS, Socket.IO або БД.
  Сервер викликає цей пакет; клієнт його не імпортує.
- **Спільні дані:** клієнт і сервер використовують `packages/shared` для
  контрактів обміну. Пакет не містить секретів, доступу до БД або повного
  прихованого стану партії. Сервер перевіряє вхідні дані під час виконання:
  самих TypeScript-типів недостатньо.

Залежності: клієнт використовує `shared`; сервер використовує `shared` і
`game`. Серверні модулі не потрапляють до клієнтської збірки.

## Автодеплой

Debian перевіряє `main` на GitHub кожні дві хвилини. Якщо коміт змінився,
окремий користувач `catan-deploy` завантажує репозиторій, збирає
`apps/client/` у новий каталог релізу й атомарно перемикає посилання
`/srv/catan/current`. Nginx віддає
сторінку за адресою `https://play.butafor.online/catan/`.
Помилка завантаження не перемикає активний реліз.

Налаштування служби, таймера та маршруту Nginx знаходяться в `deploy/`.
Поточний деплой охоплює лише зібраний клієнт; серверну частину гри ще не
запускаємо в production.

## Налаштування та секрети

Локальні параметри зберігаються у файлах `.env`, які Git ігнорує.
Приклади конфігурації без секретів можна додавати як `.env.example`.
Доступ до БД та інші секрети залишаються на сервері; змінні `VITE_*`
потрапляють у клієнтську збірку і не використовуються для секретів.

## Розробка

Після встановлення Node.js 24 LTS та залежностей:

```bash
npm install
npm run dev:server
npm run dev:client
```

Перевірки всіх workspace-пакетів запускаються командами:

```bash
npm run typecheck
npm run build
npm test
```

Сервер надає технічний endpoint `GET /health` і перший вертикальний зріз
авторизації:

```text
POST /auth/guest
POST /auth/register
POST /auth/login
GET  /auth/me
POST /auth/logout
```

Гостьова, password і Google OAuth авторизація використовують спільну серверну
сесію в `HttpOnly` cookie. Password-користувачі реєструються через
`POST /auth/register` з username і паролем, а входять через
`POST /auth/login`. Паролі не зберігаються у відкритому вигляді: використовується
Node.js `scrypt` із випадковою сіллю.

Поки
PostgreSQL ще не підключений, користувачі та сесії зберігаються у локальному
JSON-файлі `apps/server/data/mock-db.json`. Файл створюється автоматично,
ігнорується Git і призначений лише для локальної розробки та тестування.
Шлях до нього можна змінити через `MOCK_DB_PATH`.

Для Google OAuth потрібно створити OAuth 2.0 Web application у Google Cloud
Console і додати redirect URI:

```text
http://127.0.0.1:3000/auth/google/callback
```

Потім потрібно заповнити `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` і
`GOOGLE_REDIRECT_URI` у локальному `.env`. Авторизація запускається через
`GET /auth/google`; після callback сервер створює або знаходить локального
користувача та встановлює ту саму серверну session cookie, що й guest auth.
Google access token не зберігається у mock database і не передається клієнту.
Команда `npm run dev:server` завантажує змінні з кореневого `.env`; для
production змінні краще передавати через systemd environment або окремий
захищений env-файл. Node.js завантажує env-файл до запуску сервера, а
`apps/server/src/config/env.ts` перевіряє значення через Zod і створює
типізовану конфігурацію. Серверні модулі не читають `process.env` напряму.

Основні параметри сервера мають defaults `HOST=127.0.0.1`, `PORT=3000`,
session TTL 30 днів і OAuth state TTL 10 хвилин. Їх можна змінити через
`SESSION_TTL_SECONDS` та `OAUTH_STATE_TTL_SECONDS`. Google OAuth або повністю
вимкнений, або потребує одночасного заповнення `GOOGLE_CLIENT_ID`,
`GOOGLE_CLIENT_SECRET` і `GOOGLE_REDIRECT_URI`; часткова конфігурація є
помилкою запуску. `DATABASE_URL` і `CORS_ORIGIN` уже розпізнаються config
loader-ом для майбутніх server-модулів, але ще не підключають DB або CORS.

Модулі авторизації, кімнат, realtime-взаємодії, доступу до БД та ігрових сесій
розміщуються в `apps/server/src/`; їхня реалізація додаватиметься без зміни
меж пакетів `game` і `shared`.
